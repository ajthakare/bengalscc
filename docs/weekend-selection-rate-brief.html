Weekend-Level Selection Rate

Problem Brief — Golden State Cricket Club (GSCC)
Prepared: April 2026 Status: Discussion — solution not yet decided Audience: Club committee & selectors

1. Club & Team Structure

GSCC fields four competitive teams each season. The key distinction is between T20 teams (which have exclusive, committed cores) and T40/T30 teams (which draw from a shared, broader pool).

Bengal Tigers
T20 · ~15 exclusive core players
Bengal Bulls
T20 · ~15 exclusive core players (separate from Tigers)
Bengal Bears
T40 · ~4–5 core players · all roster members eligible
Bengal ThunderCats
T30 · few core players · all roster members eligible
Key rules:
  • A player is core to at most one T20 team — Tigers and Bulls cores do not overlap.
  • All ~50 club members are in the roster for Bears and ThunderCats and are eligible to play.
  • All games are on weekends. A weekend = Saturday + Sunday.
  • Multiple team fixtures can fall on the same weekend (e.g., Tigers play Saturday, ThunderCats play Sunday).

2. How Selection Is Currently Tracked

For each player, per team, per season:

Current formula
Availability Rate = timesAvailable / totalFixturesForTeam × 100
Selection Rate = gamesPlayed / timesAvailable × 100

The formula behaves differently depending on whether a player is core to that team:

Player type Fixture denominator Availability counted as Selection counted as
Core to team (e.g., core Tigers) ALL past fixtures for that team Fixture-by-fixture — missing a fixture counts against you Each game played / available
Non-core / guest (e.g., Tigers player in Bears game) Only fixtures they were selected in Always treated as available (if selected) Always 100% — selected = available

3. The Problem — Multi-Game Weekends

On weekends where multiple teams play, a player may be available for more than one game. The current fixture-level formula does not understand that these games happen on the same weekend — it treats each fixture independently. This creates unfair distortions.

Problem Scenario A — The "Bumped to Another Team" Case
Player A is core to Tigers. Tigers selectors choose someone else, but offer Player A a ThunderCats slot the same weekend.

The club gave Player A a game. They played. But the current formula says:

TeamWhat happenedWhat formula recordsFair?
Tigers Available, not selected −1 to selection rate ✗ Penalised
ThunderCats Selected, played +1 to non-core count (always 100%) Ignored effectively
Result: A player who received a game and played is penalised as if they were dropped without any compensation. Their Tigers selection rate falls even though the club did right by them.
Problem Scenario B — The Invisible Non-Core Player
Player B has no core team. They vote for every Bears and ThunderCats game all season but are never selected.
WeekendVoted forSelectedFormula records
Weekend 1Bears + TCNoneNothing (non-core, not selected)
Weekend 2Bears + TCNoneNothing
... same for all 10 weekends ...
Result: Player B shows 0 games played and 0% selection, but the formula cannot tell if they were never picked or never voted. The formula is blind to non-core availability.
Problem Scenario C — Inflated Club-Level Rate
Player C is core to Tigers (7/10 selected) and also plays 3 Bears games as a guest.
TeamGames playedTimes availableSelection rate
Tigers (core)7978%
Bears (non-core)33100%
Club total101283%
Result: Club-level selection rate (83%) overstates the picture. Guest games always add equal amounts to numerator and denominator, pulling the overall rate upward artificially.

4. What We Actually Want to Measure

The Fairness Goal

With ~50 members, we want to give equal opportunities to most players. Better players will naturally get more games, but the gap between a skilled and an average player's selection rate should not be drastically wide.

The right question to ask is: "When this player was available and willing to play, how often did the club actually give them a game — across the whole weekend?"

If a player was bumped from Tigers but given ThunderCats the same day, the club kept their promise. That should count as a successful weekend, not a failed one.

Weekend-Level Scenarios — What We Expect

Assume a typical weekend where both Tigers and ThunderCats play (Sat + Sun). Player A is core to Tigers.

# Available for Selected for Current verdict Expected verdict
W1 Tigers + TC Tigers ✓ Selected (Tigers) ✓ Got a game
W2 Tigers + TC ThunderCats only ✗ Tigers miss (penalised) ✓ Got a game
W3 Tigers + TC Both ✓✓ Selected in both ✓ Got a game (double)
W4 Tigers + TC Neither ✗ Not selected ✗ Missed weekend
W5 Tigers only Neither ✗ Not selected ✗ Missed weekend
W6 TC only TC ✓ Non-core game ✓ Got a game
W7 TC only Neither — (non-core, not counted) ✗ Missed weekend
W8 Neither — — (not counted) — (not counted, absent)

W2 is the critical broken case. W7 is also broken — the player showed up and voted but got nothing, and the current formula silently ignores it.

5. Proposed Solutions

Solution 1 Weekend Selection Rate — New Additive Metric

Group all fixtures by weekend (Sat–Sun pair). For each weekend where a player was available for at least one game, record whether they were selected for any game that weekend.

New formula (weekend level)
Weekend Selection Rate = weekends_selected_in_any_game / weekends_available_for_any_game × 100
Weekend Availability Rate = weekends_available / weekends_core_team_played × 100 (core players only)

  • Weekend selection rate: 67% (Wk 3 = got a game)
  • Per-team stats: unchanged
  • Clear fairness signal

Pros & Cons

✗Adds a new metric — need to decide where to display it
✗Requires grouping fixtures by Sat–Sun pair in the calculation engine
Solution 2 Availability-Adjusted Core Team Rate

Keep the fixture-level formula but change what counts as a "miss" for a core team. If a player was not selected for their core game but was selected for another game the same weekend, don't penalise their core team rate.

Modified rule — core team selection numerator
Count as selected if: wasSelected_core_game = true
                   OR (wasSelected_core_game = false AND wasSelected_any_other_game_same_weekend = true)

Example — Wk 3 from above (Tigers + TC weekend)

FixturewasSelectedCurrent rateAdjusted rate
Tigers✗−1 missNo miss (TC covered it)
ThunderCats✓+1 non-core (100%)+1 core adjustment

Pros & Cons

✓Fixes the "bumped but compensated" scenario directly
✓No new metric — modifies the existing selection rate
✗Changes existing numbers — historical comparisons shift
✗Harder to explain to players why their rate changed
✗Doesn't fix the non-core visibility problem (Scenario B)
Solution 3 Dual-Layer Stats Recommended

Keep all per-team stats exactly as they are today (useful for selectors). Add a new Weekend Participation layer alongside them for fairness reporting.

Two views, two purposes

LayerGranularityPurposeAudience
Per-team stats
(unchanged)		 Per fixture Team selection decisions — how reliable is this player for my specific team? Selectors
Weekend stats
(new)		 Per Sat–Sun weekend Fairness reporting — is every player getting a proportional share of opportunities? Committee, all members

New weekend-level fields per player per season

weekendsAvailableWeekends where they were marked available for at least one game

weekendAvailabilityRateweekendsAvailable / weekendsTotal × 100

6. Open Questions for Discussion

  • Which solution? Solutions 1 and 3 are essentially the same metric. The choice is whether to keep per-team stats and add weekend stats alongside (Solution 3), or replace the headline rate with weekend stats (Solution 1). Solution 2 is a different approach that modifies existing numbers rather than adding a new view.
  • Denominator for core players' weekend availability. Should weekendsTotal count "all weekends the core team played" or "all weekends in the season where any fixture occurred"? The first option is stricter for T20 core players.
  • What counts as "the same weekend"? Saturday + Sunday of the same calendar week is the working assumption. Does a Monday fixture (rare) belong to the previous or the next weekend?
  • Should we enforce the no-dual-T20-core rule in code? Currently nothing prevents an admin from accidentally marking a player as core to both Tigers and Bulls. Should the system warn or block this?
  • Where should weekend stats appear in the admin UI? Options: a new column in the existing statistics table, a separate "Weekend Summary" tab, or a fairness report page visible to committee members.
